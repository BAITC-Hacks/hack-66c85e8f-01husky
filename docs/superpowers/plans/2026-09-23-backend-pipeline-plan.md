# План backend + pipeline

Дата: 2026-09-23. База проверки: `develop` на `fac817b`, после PR #1 и #2.
Рабочая ветка: `feat/pipeline`. План по фактическому коду и полному кейсу пользователя.

## Ответственность и ограничения

- Ардак принимает `backend/`, `pipeline/`, Compose, env, тесты интеграции и документацию запуска. Бота реализует другой участник; в этой ветке его не разрабатываем.
- Frontend остаётся у Эмира; согласуем API, уведомление о записи и совместный сценарий приёмки.
- Передача аудио и текста во внешние облачные API запрещена, включая разработку и демо. Модели только локальные/self-hosted. Загрузка весов — отдельный подготовительный этап, при обработке сеть наружу не нужна.
- Design spec обновлён: облачные dev-провайдеры исключены, backend передан Ардаку, bots — другому участнику. Контракт `MeetingResult` сохраняем; необходимые расширения фиксируем отдельно.
- Обязательные функции и приватность — первая очередь. Дополнительные функции остаются в плане, но не блокируют первый сквозной результат. Реальная СЭД и промышленное развёртывание вне обязательного объёма.

## Результат этапа 1 — 23.09.2026

- Подняты локальные PostgreSQL 16 и Redis с отдельными паролями, применены миграции/seed; API работает на localhost:8000, worker/beat запущены.
- Общий offline Whisper используется CLI и backend. Настройки и зависимости закреплены, телефоны/ИИН маскируются перед сохранением; это не полная анонимизация.
- Настоящий HTTP → Redis/Celery → Whisper → PostgreSQL прогон записи №1 завершён: встреча №1, 47 сегментов, статус `draft`. Нет фиктивных поручений и спикеров.
- 67 backend-тестов и 19 pipeline-тестов прошли, HTTP smoke проверил DOCX/PDF. Ошибки модели/декодирования и тишина покрыты unit-тестами с подменой модели; это не проверка качества модели.
- Дополнительно реальная кешированная модель проверена на тишине и повреждённом файле с запретом Python socket-подключений. Перезапуск API/worker не потерял транскрипт; cookie-login и CORS для 3000/5173 проверены HTTP-запросами.
- `.dockerignore` исключает записи и кеш весов. Контейнерный ML-запуск и проверка с заблокированной внешней сетью остаются на этапе 5.
- Инструкция: [локальная разработка](../../local-development.md). Следующий этап — RU/KK/mixed и диаризация; бот не входит в нашу реализацию.

## Этап 1. Проверяемая основа и соединение STT с backend

- Подготовить изолированные PostgreSQL и Redis для тестов; проверить миграции, seed, backend pytest и HTTP smoke. Не запускать fixtures с `drop_all`/`TRUNCATE` на пользовательской БД.
- Перенести загрузку Whisper и транскрипцию в `pipeline/pipeline/stt/local_whisper.py`; CLI должен пользоваться тем же кодом.
- Лениво загружать и кешировать модель, задавать путь к весам и режим вычислений конфигурацией. По умолчанию обработка offline; отсутствие весов даёт понятную ошибку, без скрытой загрузки.
- Подключить STT к `real.process()` и Celery, выдавать прогресс и `MeetingResult`. На промежуточном этапе явно обозначать отсутствие диаризации и извлечения: не генерировать фиктивные задачи или уверенное определение человека.
- Объединить управление зависимостями через pyproject/lock; предусмотреть ML-зависимости именно для worker.
- Добавить privacy-маскирование перед сохранением текста и перед последующими этапами, исключить сырой текст из логов ошибок.

**Готово:** загрузка MP3 через API с `PIPELINE_FAKE=0` возвращает реальный транскрипт из БД; повторный запрос читает сохранённые сегменты. Проверены ошибка модели, повреждённый файл и тишина. Аудио/текст не уходят наружу.

## Этап 2. RU / KK / смешанная речь и диаризация

**Частично выполнен 23.09.2026:** добавлена локальная диаризация sherpa-onnx
(pyannote segmentation 3.0 + TitaNet-large) и совмещение с таймкодами слов Whisper.
Запись №2 (206 секунд) прошла HTTP → очередь → модели → PostgreSQL: встреча №2,
94 фрагмента, 6 акустических групп `speaker1`–`speaker6`, без привязки имён.
Все слова получили пересечение с интервалами голосов, 3 слова попали в перекрывающиеся
интервалы; это не подтверждает точность распознавания говорящих. Отдельный запуск
диаризации занял около 14 секунд на M4. 78 backend-тестов и 28 pipeline-тестов прошли.
Эталонная RU/KK/mixed разметка, измерение DER/WER и ручная оценка остаются открытыми.
Первое тестовое совещание удалено из рабочей БД по просьбе пользователя, локальный архив сохранён.

- Подготовить эталонную разметку трёх типов речи: исправленный текст, временные границы говорящих, участники и ожидаемые поручения. Для демо использовать смоделированную/анонимизированную запись.
- Прогнать записи №1/№2 и казахскую/смешанную запись; сравнить автоязык и `ru`, для казахской записи также `kk`. Общий язык файла не считать языком каждого сегмента.
- Добавить локальную диаризацию и совместить её интервалы с word timestamps Whisper; проверить перебивания и короткие реплики.
- Сохранять стабильные внутри встречи `speaker1`, `speaker2`, …, позволять секретарю назначить участника. Не считать обращение «Айбек, сделай» доказательством того, кто сейчас говорит. Имена, присланные ботом, без привязанных таймкодов/дорожек также не доказывают личность голоса.
- Измерить ошибки распознавания, разделения спикеров, время и память на целевом железе. Зафиксировать результат, а не обещанную скорость.

**Готово:** реальная запись с минимум тремя голосами даёт проверяемые сегменты; русский, казахский и смешанная речь оценены вручную и метриками. Ошибочные/неизвестные идентичности можно исправить.

## Этап 3. Локальное извлечение поручений и summary

- Поднять Ollama/self-hosted LLM; выбрать модель по качеству RU/KK и доступной памяти после замера. Схемы ответов валидировать Pydantic, число повторных запросов ограничить.
- Реализовать шаги: кандидаты → дословная проверка цитаты в указанном сегменте → сроки → ответственный → срочность/направление. Проверка цитаты и типовые даты выполняются кодом.
- Нормализовать сроки относительно даты встречи: ru/kk, переход месяца/года, «среда», «келесі аптаға дейін», отсутствие срока и уточнение ранее названного срока.
- Обрабатывать отмену/переназначение и дубли поручений. Не назначать исполнителем автоматически автора реплики: различать «я сделаю» и «Данияр сделает».
- Неизвестные исполнитель/срок оставлять неопределёнными. Для неоднозначных дат сохранять исходную формулировку и давать секретарю исправить результат.
- Summary RU/KK: тема, решения, поручения, открытые вопросы; только по содержимому встречи. Текст транскрипта рассматривается как данные, а не инструкции модели.

**Готово:** на размеченной записи сопоставлены ожидаемые и найденные поручения, даты, исполнители; у каждого поручения проверена цитата. Summary не добавляет фактов. JSON разбирается backend и экспортируется.

## Этап 4. Доработки backend и пользовательского сценария

Выявленные по коду места для исправления и регрессионных тестов:

- `services/speakers.py`: `recalc_assignees()` ищет имя, но не читает `speaker_map`. Нужна связь основания назначения со спикером для «я сделаю»; явное поручение другому человеку должно сохранять исполнителя. При необходимости расширить контракт/БД после согласования с frontend.
- `tasks/reminders.py`: `due_soon` уведомляет только исполнителя, а создателя — только при просрочке. Кейс требует напоминания руководителю/куратору и при приближении срока. Предложение для MVP: создатель встречи выполняет роль куратора; зафиксировать семантику явно.
- `routers/meetings.py`: query-параметры `date_from/date_to` расходятся с `from/to` в спецификации. Привести OpenAPI и frontend к одному контракту с совместимыми aliases.
- `routers/tasks.py`: проверять существование исполнителя/направления до записи, возвращать понятные 4xx; закрепить правила редактирования после подтверждения и влияние изменения срока на уведомления.
- Проверить повторную постановку Celery-задачи, повторное подключение live-записи, конкурентную обработку одной встречи и восстановление после сбоя worker; обеспечить отсутствие дубликатов и потери ручных правок.
- Не подставлять всех участников организации при пустом списке участников встречи без явной причины; проверить границы доступа и результаты сопоставления.
- Ограничить размер/длительность загрузки, проверить обработку имён файлов голосовых образцов, удаление аудио/эталонов и отсутствие чувствительных данных в ответах ошибок.

**Готово:** секретарь загружает запись → видит черновик → исправляет спикера/ответственного/срок → подтверждает → скачивает DOCX/PDF. Исполнитель и куратор получают нужные уведомления; переходы статусов и права проверены тестами.

## Порядок работы и приёмка

Наш порядок: этап 1 → 2 → 3 → 4 → 5 → 7. Этап 6 выполняет другой участник. Подготовку README и эталонных данных вести с первого этапа. Исправления backend, которые блокируют интеграцию, выполнять сразу при обнаружении.

Каждый этап заканчивается проверяемым изменением в `feat/pipeline`; слияние в `develop` — через PR. Frontend/API-изменения фиксируются до интеграции. Реализованную часть см. в результатах этапа 1 выше; остальные этапы остаются планом.

Основная приёмка: минимум RU, KK и mixed записи; у каждой проверены текст, спикеры, задачи/сроки/ответственные, summary и экспорт. Сохранить таблицу «ожидали / получили», ошибки и измеренное время. Напоминания проверить с управляемыми датами. Для итогового демо не подменять результат реальной модели fake-фикстурой.

Приоритет по оценке: рабочий сценарий и техническая интеграция (50 баллов) + README/воспроизводимость (25) прежде расширений. Время ручной проверки секретарём и видимость сроков показывают прикладную ценность (15); проверяемые цитаты, смешанная речь и локальная обработка дают основания для развития (10).
