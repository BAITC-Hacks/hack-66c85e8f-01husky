# Локальное разделение говорящих

Whisper распознаёт текст, но сам не определяет, кому принадлежит голос. Прежний
`SPEAKER_UNKNOWN` был явной заглушкой этапа STT. Теперь `pipeline.real.process`
добавляет акустическую диаризацию. Отдельный локальный LLM-этап может установить
имя по явной передаче слова или представлению, но не по порядку списка участников.

## Как работает

1. Whisper распознаёт текст с таймкодами отдельных слов.
2. Локальная модель pyannote segmentation 3.0 находит интервалы голосов.
3. NeMo TitaNet-large вычисляет голосовые векторы; кластеризация sherpa-onnx
   объединяет похожие голоса в пределах встречи. Векторы не сохраняются в БД.
4. Каждое слово получает голос по максимальному пересечению с интервалом.
   Если внутри реплики меняется голос, реплика разделяется; слово не дублируется.
   Короткий сдвиг границы в хвосте предложения (до 1,2 с) переносится к его концу,
   только если в месте границы нет паузы ≥0,20 с/перекрытия голосов и следующий акустический голос
   продолжается дальше. Исправление не объединяет кластеры и не меняет текст.
5. Метки нумеруются по первому появлению: `speaker1`, `speaker2`, … и сохраняются
   в `segments` и `speaker_map`. Телефоны/ИИН маскируются перед сохранением,
   в том числе если телефон оказался на границе двух фрагментов.

Метки действуют **только внутри одной встречи**. Это не распознавание личности:
`speaker1` во второй встрече не обязательно тот же человек, что в первой.
`participant_id=null`, `source=none`, `confidence=0` означают неизвестное имя.
Готовый API ручного сопоставления `PUT /api/v1/meetings/{id}/speakers` сохраняется.
Voiceprint-enrollment и автоматическое узнавание человека по эталону ещё не готовы.

## Модели и подготовка

```bash
uv sync --project backend --extra stt
backend/.venv/bin/python -m pipeline.download_diarization_models
```

Скрипт получает только веса (около 108 МБ загрузки) из официальных релизов sherpa-onnx,
проверяет закреплённые SHA-256 ONNX-файлов и сохраняет их в
`pipeline/.models/diarization/`. При обработке ни скачивания, ни внешних API нет.
Если веса отсутствуют, обработка завершается ошибкой, а не фиктивными голосами.
Для закрытого контура перенесите весь каталог вместе с лицензиями.

Использованные модели и происхождение:

- [pyannote/segmentation-3.0](https://huggingface.co/pyannote/segmentation-3.0),
  CNRS, MIT; ONNX-конвертация из
  [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/models.html).
  LICENSE сохраняется вместе с весами.
- [NVIDIA TitaNet-large](https://huggingface.co/nvidia/speakerverification_en_titanet_large),
  CC BY 4.0; готовая ONNX-конвертация `nemo_en_titanet_large.onnx` из
  [релиза sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models).
  Это локальный файл NVIDIA-модели, **не облачный NVIDIA API**; сами веса нами не изменялись.

## Настройки в .env

```dotenv
# По умолчанию pipeline/.models/diarization
# DIARIZATION_MODEL_DIR=/absolute/path/to/models/diarization
DIARIZATION_CPU_THREADS=4
DIARIZATION_THRESHOLD=0.5
DIARIZATION_BOUNDARY_GRACE_SEC=1.2
# Не задавайте, если реальное число говорящих неизвестно:
# DIARIZATION_NUM_SPEAKERS=3
```

Без заданного числа говорящих кластеризация оценивает его автоматически. Больший
порог объединяет больше голосов, меньший может разделить одного человека на несколько.
Не подгоняйте число по списку приглашённых: часть участников может молчать.
После смены настроек перезапустите API/worker через `scripts/local_dev.py`.
`DIARIZATION_BOUNDARY_GRACE_SEC=0` отключает коррекцию границ. Это эвристика, не
новая модель тембра: перебивание без паузы может быть распознано неверно.
Число скорректированных слов записывается в `alignment_adjusted_boundary_words`.
Имена с источником `llm` имеют эвристическую confidence 0,75 (не калиброванную
вероятность); противоречащие привязки одного голоса остаются неизвестными.

## Проверка и ограничения

```bash
backend/.venv/bin/python scripts/smoke_local_stt.py "pipeline/recordings/Совещание №2.mp3" --min-speakers 2
```

Создаётся новая dev-встреча; проверяются сохранённый текст, последовательные speaker-метки
и дословность цитат поручений. Для полного прогона нужна [локальная LLM](local-llm.md).
Результат смотрите в `/admin` → «Транскрипт»
с фильтром по ID встречи и в «Говорящие». Качество нужно проверять на слух по таймкодам.

Проверено 23.09.2026 на Apple M4: запись №2 длительностью 206 секунд дала 94 фрагмента
и 6 групп голосов в БД. Чистая диаризация заняла около 14 секунд (без STT).
`alignment_nearest_words=0`, `alignment_distant_words=0`, `alignment_coarse_segments=0`,
`alignment_overlapping_words=3`. Качество кластеризации и реальное число участников
требуют ручной проверки; речь и голоса не подменялись фикстурой.

Регрессия 00:55 этой записи: исходные 94 фрагмента после коррекции дают 93.
Вопрос 55,02–56,66 с целиком остаётся у `speaker3`, ответ с 56,66 с — `speaker4`.
Скорректированы 4 слова. Короткое перекрытие в **начале** вопроса больше не блокирует
исправление более поздней чистой границы. Это проверка конкретного дефекта,
не доказательство правильной атрибуции всех голосов и не оценка DER.
После объединения ASR-обрывов в предложения одного спикера получается 72 сегмента;
проверяемые цитаты поручений ссылаются уже на эти финальные индексы.

Короткие ответы, похожие голоса, шум и одновременная речь могут давать ошибки. TitaNet
обучался на преимущественно английских данных; точность для RU/KK/mixed не гарантирована.
Для слова на границе VAD выбирается ближайший интервал; счётчики таких случаев
(`alignment_nearest_words`, особенно `alignment_distant_words` > 0,75 с), одновременной
речи (`alignment_overlapping_words`) и грубой сегментной привязки при отсутствии
таймкодов слов (`alignment_coarse_segments`) записываются в `model_info`.
Это диагностические счётчики, не confidence личности и не измеренная DER.

Одно слово контракт относит одному говорящему: одновременную речь не разделяем на
отдельные аудиодорожки. Полностью пустая диаризация при непустом тексте — ошибка;
тишина с пустым текстом не создаёт говорящих.

Будущий бот может присылать имена участников, но для автоматической связи с голосом
нужны метки активного участника с таймкодами, отдельные дорожки или проверенные эталоны.
Один список имён не даёт такой связи. Разработка бота остаётся у другого участника.
